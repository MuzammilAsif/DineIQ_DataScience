## Task

## Features used

Only raw metrics from `parquet_data/features/item_features/`:

`item_revenue`, `item_cost`, `contribution_margin`, `profit_percentage`, `total_quantity_sold`, `item_popularity`, `order_frequency`, `repeat_purchase_rate`, `average_rating`, `rating_trend`, `wastage_percentage`, `promotion_dependency`, `discount_percentage`, `price_change_percentage`, `weekend_order_ratio`, `sales_trend`.

Excluded because Step 4 built the label from them: the four percentiles and tiers (profitability, demand, quality, wastage), `quality_score`, all ten flags and `category` itself. `tests/test_menu_classification_model.py` asserts none of them reaches the feature vector.

The label is still a deterministic function of percentile ranks of `profit_percentage`, `total_quantity_sold`, `wastage_percentage`, `average_rating` and `repeat_purchase_rate`, all of which are features here in raw form. A percentile is a monotonic transform of the raw value within one snapshot, so tree models can approximate the rule's cut points closely. High scores are expected for that reason. The learned cut points are absolute values, while the rule's are relative to each snapshot's population, so the model needs retraining when the menu's overall distribution shifts.

**Preprocessing:**

- Nulls in `price_change_percentage`, `rating_trend`, `sales_trend` are set to 0. A null price change means the price never changed, and a null trend means no clear trend (under 3 months of data). These are values, not defects, so no rows are dropped.
- Any remaining null is imputed with the training median (`Imputer` inside the pipeline). The current snapshot has none after the step above.
- `StringIndexer` on `category`, alphabetical order, fitted once on the whole set so label indices are fixed. `IndexToString` at the end of the pipeline decodes predictions.
- `VectorAssembler` over the 16 features. `StandardScaler` (mean and std) only in the Logistic Regression pipeline; the tree pipelines use the unscaled vector.
- Balanced class weights, `n / (k * n_class)`, computed on the training portion and passed as `weightCol`. Profit Driver has about 5x fewer items than Low Performer, and macro F1 weights every class equally.

## Split and cross-validation

- Held-out test set: `sampleBy("category", 0.2 per class, seed=42)`. `sampleBy` samples each row independently, so class counts are close to 20% but not exact.
- The remaining rows go to `CrossValidator` with 5 folds. Folds are assigned per class, round-robin in random order (`foldCol`), so every fold holds every class. Spark's default random folds could leave a fold with no Profit Driver.
- Tuning metric: macro F1 through a custom evaluator. Spark's `MulticlassClassificationEvaluator(metricName="f1")` returns weighted F1, which over-weights the large classes.
- Macro F1 is the unweighted mean of `MulticlassMetrics.fMeasure(label)` over the four classes.

## Final model

**RandomForestClassifier** (numTrees=30, maxDepth=10): held-out macro F1 0.914, accuracy 0.929, weighted F1 0.928.

Selected by held-out macro F1, with CV macro F1 as the tie-break. Accuracy is not the selection metric: with Low Performer at 38% of items and Profit Driver at 8%, a model can score well on accuracy while missing Profit Drivers, and macro F1 penalises that.

SRS target: accuracy >= 0.85 and macro F1 >= 0.80. Result: accuracy 0.929 (met), macro F1 0.914 (met). These are the real held-out numbers; no hyperparameter was tuned on the test set.

Choosing among the three tuned models by test score is itself a selection on the test set, so the winner's test figure is somewhat optimistic. DecisionTreeClassifier had the best CV macro F1 (0.884) but a test macro F1 of 0.798, which shows how much a 28-item test set can reorder the models.

## Reliability of these numbers

Every class with fewer than 10 test items is too small for its per-class metric to be trusted: Hidden Opportunity (5), Profit Driver (4), Volume Driver (7).

One misclassified item moves a class's recall by 1/n: for the smallest class (4 items) that is 25%. The test set has 28 items, so one error moves accuracy by 3.6%. Treat the per-class test figures as indicative only. The CV macro F1 (5 folds, every training item scored once) is the more stable estimate: 0.822 +/- 0.136 for the final model, against 0.914 held out, a gap of 0.092 (within one fold standard deviation).

There are only ~150 labelled items, so this task will not be used for the SRS's 100+ unseen-record dual-pipeline comparison. That will be a higher-row task in a later step. This step covers the requirement to train and compare at least three Spark MLlib algorithms.
